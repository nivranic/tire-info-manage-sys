# PostgreSQL 升级库与运行合同兼容计划

**Goal:** 验证已支持的旧 PG 升级路径可以在保留业务数据与约束的前提下进入 verify 启动；不把未知运行结构签成可信参考。

**Architecture:** 先在全新隔离 PG 重现旧结构的增量迁移，捕获升级库与空参考库的逐项差异。仅对实测且不影响应用语义的表示差异做确定性规范化；类型、默认值、约束、索引和保护机制继续精确比较。真实历史制品、合成旧结构和部署旧库分别留证。

**Tech Stack:** PostgreSQL 18、SQLAlchemy catalog、现有运行合同及隔离验收脚本。

## 顺序

1. 复用 `scripts/verify-postgres.ps1` 的全新集群、TLS 和退出清理，在私有诊断槽构造现有 core 已覆盖的 001–004 缺列旧结构；保留迁移前后行及版本指纹，输出与空参考合同的结构差异。
2. 若只有列物理顺序差异，审查消费者是否依赖列位置。评估固定按列名称排序（无需改表）、维护窗口物理重建（有数据／锁风险）、按历史分支维护多份参考（合同维护复杂度）三种方法；以实测证据决定，不自动放宽任何类型或约束。
3. 在 `scripts/postgres_schema_acceptance.py` 添加旧结构升级、重复迁移、非拥有者 verify、历史行保持及结构反例；必要时最小修改 `apps/api/tire_api/postgres_schema.py`。先记录原实现失败，再跑同一验收入口。
4. 若能从已有正式 Git 提交安全重建历史 PG schema，另外验证真实历史代码生成的库；不能用合成缺列测试冒充部署旧库验收。历史代码不得连接正常数据库或真实 Provider。
5. 运行受管启动／迁移／CLI／Worker 回归和真实 PG runtime-schema 验收；核对输入绑定、资源关闭及历史失败保留。
6. 更新 `docs/POSTGRES-RUNTIME-SCHEMA.md`、本轮验收和 `docs/AGENT-HANDOFF-CURRENT.md`；注明兼容范围、合同重建要求与尚未覆盖的旧库。提交并推送正式结果，独立核对远端。

## 验收与边界

- 旧列值、旧行、旧版本时间不得被改写，新增可空历史字段保持 SQL NULL，不补造身份或验证结果。
- 升级后成功只证明明确的历史路径；不推断任意部署库、PG major、RLS 或生产最小权限已通过。
- 不重签未知运行库，不扩大运行角色权限，不删除结构反例；生产库、原规格、KIT C2 和封存历史尾文保持。
- 完整 V1 的其余要求继续开放。
