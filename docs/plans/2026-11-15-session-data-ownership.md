# 会话资料归属与登录轮换实施计划

目标是消除同浏览器换人后报告、AI历史、偏好等资料随会话重绑而转移的问题，并保留同账户多会话读取、正常匿名使用和已受理后台任务的归属。基线为已发布 `b393b25`。原始失败见上一阶段验收及本机Git忽略回执。

## 设计决定

已复核三种实现路径。仅轮换cookie需要同时处理历史资料锚点，独立凭据表需要扩大所有认证入口及迁移范围。在既有 `local_sessions` 中保存持久归属，可以复用当前actor_session_id和账户读取逻辑，因此采用此方案。

1. 新增 `owner_user_id` 保存已确认的持久用户归属，`user_id`继续表示当前登录绑定。`session_scope`按持久归属聚合，`current_user`只认可仍有效的登录状态。
2. 新增内部 `anonymous_claimable` 标记。新建的正常匿名会话可在首次登录时把匿名资料一次性归入该账户。旧库已有明确user_id的会话回填owner_user_id，旧库无用户绑定的会话保持归属待确认，自动认领标记为false。历史上已经发生的错绑需要另外核对原始归属证据。
3. 登录、注册和已登录退出均轮换会话ID。旧会话过期并撤销user_id绑定，持久owner保留。注册、归属认领和新会话写入处于同一写锁事务，响应成功后由现有中间件统一签发cookie。
4. 过期清理、在线／CLI密码重置及删除账户保留持久owner，撤销当前user_id。删除后的旧资料锚点和原件保留，旧cookie下一次请求进入新匿名会话。
5. 沿现有账户代次模式为报告和AI加页面重验与销毁边界，覆盖迟到结果。后台已受理任务继续沿原持久归属使用记录。车库当前采用local_workspace共享范围，账户私有化列入完整V1后续范围。

6. 报告保存的内存恢复按账户分区。AI恢复指针按账户保存在sessionStorage，新匿名调用指针只保存在当前账户代次内存中，刷新后通过服务端历史恢复。既有无归属指针停止自动采用。
7. 私人监控通知按持久owner路由到该账户的订阅，并核对该账户存在有效登录。同账户重新登录后可继续投递，另一个账户的登录不会恢复前账户的投递资格。
