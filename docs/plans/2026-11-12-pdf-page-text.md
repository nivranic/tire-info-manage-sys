# PDF逐页正文与引用实施计划

本计划执行原文RAG计划第3步，采用brainstorming与writing-plans流程，沿既有main实施。

## 交付范围

为已保存PDF提供受限进程逐页抽取、无可抽取文字／加密状态、可重建FTS投影及页码引用恢复。入口接入既有原始文档界面、知识检索、共享协议与SDK，保留原件及原始凭证的事实状态。正文引用绑定文档、元信息指纹、原始SHA256、抽取版本、页码和页内Unicode码点区间。Provider与导出用途继续通过各自现行合同核验。

## 实施顺序

1. 新增 `apps/api/tire_api/document_pdf.py`，将pypdf加入生产依赖。在现有 `parser_runtime.py`、`parser_child.py` 和 `parser_bundles.py` 注册固定内部PDF能力，复用GO握手、时间／CPU／内存边界、并发限制和进程回收。八、九、十来源归档清单保留各自能力集合。
2. 新增 `document_text_models.py`、`document_text.py` 及034迁移，保存文档投影、逐页文字及分块。SQLite采用FTS5，PostgreSQL采用GIN。提取在原件校验后执行，提交前重新核对文档绑定，派生状态与分块在同一事务发布。失败记录进入现有审计，原始凭证继续保留。
3. 提供文档正文索引、逐页读取、PDF正文检索及原件引用恢复API。引用恢复从原件重新抽取，派生投影清空后仍可按原引用恢复。搜索仅消费已明确建立的PDF正文索引，返回文档范围和原始许可说明。
4. 在共享协议和SDK增加PDF正文合同，通过既有原始文档入口提供索引／逐页查看，并在符合文档范围的历史知识检索中展示PDF命中与引用恢复。
5. 执行相关API／迁移／原始对象回归、真实受限Parser、归档清单兼容、SDK、三端类型、生产构建及隔离浏览器验证。继续核对PostgreSQL实际查询与备份恢复，记录各批来源、源码绑定和资源关闭结果。

## 验证入口

- `apps/api/tests/test_document_pdf.py` 覆盖逐页文字、Unicode、空页、加密、损坏和边界，以及真实子进程回执。
- `apps/api/tests/test_document_text.py` 覆盖生产API、分页、页码引用、丢失投影、对象损坏、事务失败及正式材料许可绑定。
- `scripts/run_api_worker_regression.py` 登记新模块，受管批使用新私有槽。子进程受审源码哈希在审查实际修改后同步。
- `packages/api-client/tests/` 补齐请求、版本与取消合同。浏览器使用合成PDF，覆盖索引、逐页查看、正文检索、引用恢复及关闭／迟到响应。

完整原文RAG继续覆盖后续正文向量、融合／重排、证据包与真实Responses语义。

## 当前交付停点

已实现受限逐页抽取、034派生索引、四个生产API、共享SDK及原始文档逐页面板。抽取区分全部有字、部分有字、无可抽取文字和加密状态。引用从保存原件重新抽取，按文档元信息指纹、原件哈希、抽取版本、页码及页内Unicode码点区间核对。

九模块广批执行332项，其中331通过、1失败，PDF两模块36项均通过。失败为历史十来源清单与当前十一项清单整体相等的陈旧断言。修正比较范围并同步受审源码哈希后，完整Parser包模块25／25通过，787个输入稳定、资源关闭且非自检拒绝0。广批后的源码变更范围为该测试文件及其受审哈希清单。两个回执分别位于 `.artifacts/pdfh-r1/` 和 `.artifacts/pdfh-r2/`。

PDF SDK7／7、既有正文SDK9／9、Web50／50、三端类型及独立Web生产构建通过，629个前端输入逐字节匹配。pypdf生产依赖已同步uv锁文件。受管清单20个文件的现行LF／CRLF格式通过 `.gitattributes` 固定，自动换行开启与关闭的40项Git过滤检查通过。相关交付检查在 `.artifacts/pdf-handoff-20261112/`。
