# PostgreSQL 迁移与运行启动分离计划

**Goal:** API／Worker 可在无数据库对象拥有权的 PG 账户下启动，启动阶段只校验经过批准的完整 schema 合同，不执行 DDL 或自动迁移。

**Architecture:** 保留既有本地 migrate 启动路径，新增显式 verify 模式。参考合同只在空的隔离 PG 参考库运行当前迁移后生成，绑定包内 Python 源码、PG major、结构及外部指定的文件 SHA-256。运行库只能与已批准合同比较，不能自动捕获自身结构作为期望。

**Tech Stack:** SQLAlchemy、PostgreSQL catalog、SHA-256、现有受管测试与隔离 PG。

## 实施

1. 将 db.py 模型注册与迁移执行拆成可复用内部步骤，保持 SQLite 和原迁移事务／锁不变。核对仅 Database 和 API factory 两种导入路径的模型集合一致。
2. 新 schema 模块捕获 public 表／列／约束／索引／触发器（含 FK 内部保护状态）／函数／版本与扩展。定义有界、固定的结构格式；排除所有者名、OID、业务数据及机器路径；固定 search_path 和超时。普通运行账户可只读比对。
3. 参考构建入口仅接受明确 PG 配置和空参考库，在原 schema 锁内迁移后捕获。配置和密码复用既有显式 PG 连接工具，输出文件必须全新。不从已有运行库签发合同，不自动创建数据库／角色。
4. Database 新增 opt-in verify 设置，API／Worker 通过统一初始化入口使用它；verify 要求 PG、绝对合同路径和独立固定 SHA。缺文件、摘要／源码／版本／结构差异均固定拒绝；运行模式禁止恢复到 migrate 或 SQLite。
5. 在 test_schema_startup.py 增加配置、拒绝和无 DDL 分派反例；原有 SQLite 并发／失败回滚继续通过。真实 PG 验收包含参考生成、非拥有者启动、正常 HTTP／Worker、缺表／列／约束／索引／触发器／函数／版本／扩展和合同／源码损坏拒绝，并核对无 DDL、无 schema 写入及连接释放。
6. 补部署说明与交接、保留原始失败、提交／推送并独立核对远端。生产 IAM／RLS、完整 DML 最小权限、远端和性能验收仍逐项推进。

## 信任与运维边界

合同来自受控空参考库和当前源码，并由部署者审查、固定摘要。它不是对恶意 DBA、篡改的 PostgreSQL 服务端或部署环境的证明。升级时先完成独立迁移验收，再更新运行合同；不得为适应未知差异直接重签生产库。已有升级库物理结构与新库不同则明确拒绝，须评估迁移兼容性，不隐式忽略。

启动核验是维护窗口中的结构快照，不承诺阻止后续 DBA DDL。默认本地行为保留，显式 verify 的失败不能降级。此切片不把完整服务器部署、OIDC／RLS 或全部端点最小权限认定为完成。
